# Scale run

Generated by `python -m tasleem.loadtest --patients 5000` on 16 Nov 2026.
Synthetic patients only. One process, sqlite file database, no Redis. This is a floor for one API
replica on a laptop, not a cluster benchmark. Production runs on PostgreSQL with several replicas.

| Measure | Result |
|---|---|
| Patients / inbound messages | 5,000 / 29,099 |
| Cases / audit events written | 5,000 / 37,531 |
| Ingest (full path: parse, dedupe, engine, hash chain, commit) | 235.4 messages/s (123.6 s total) |
| Scheduler drain over all due cases | 4,395 checked in 13.57 s, 9 batches, 0 conflicts |
| Worklist page of 50 (risk-ordered, index-backed) | p50 18.3 ms, p95 20.1 ms |
| Case detail with full timeline | p50 1.1 ms, p95 1.2 ms |
| Program metrics, cold full scan / cached | 238.1 ms / 0.01 ms |
| Audit chains verified (random sample) | 200 checked, 0 broken |
| Open cases without an owner (R1) | 0 |
| "Completed" status with no report detected (false done) | 360 |
| Open stalls flagged | 4,216 |

What scales with what: ingest cost is per message and did not grow with case count; worklist and
detail reads are index-backed and flat; the metrics scan is linear in cases but cached, with staleness
bounded at 15 s by default, so it runs at most a few times a minute regardless of dashboard traffic.
Only FIT-positive results open a case, so live open-case counts are a small fraction of people screened.
Bulk backfills are the load to plan for: run them through the queue (TSL-045) with several workers.
